# HTB Writeup: Fireflow 💻🔥

**Nível:** Medium | **OS:** Linux | **Temas:** Web Enumeration, CVE Exploitation, JWT Bypass, Kubernetes

Este writeup documenta o processo completo de exploração da máquina **Fireflow** do Hack The Box, desde o mapeamento inicial da superfície de ataque até a escalação de privilégios em um ambiente Kubernetes.

---

## 🔍 1. Reconhecimento (Reconnaissance)

O processo começou com a varredura das portas e serviços expostos no alvo (`10.129.68.211`).

### Nmap Scan
O escaneamento identificou os seguintes serviços principais:
* **Porta 22:** SSH (OpenSSH 9.6p1)
* **Porta 443:** Nginx (HTTPS)
* Múltiplas portas altas em estado `filtered`, indicando a presença de serviços internos isolados por regras de firewall.

### Enumeração Web & OSINT
A análise do tráfego web na porta 443 foi o ponto de partida para a descoberta da aplicação:
1. O acesso a `https://fireflow.htb` expôs e-mails corporativos (`ops@fireflow.htb`) e headers HTTP de segurança (`X-Frame-Options`) que revelaram a existência do subdomínio `flow.fireflow.htb`.
2. Após adicionar os endereços ao `/etc/hosts`, a exploração do subdomínio revelou uma interface do **Langflow**.
3. Abandonando testes manuais de injeção na interface web (rabbit holes), a estratégia pivotou para a extração de metadados.
4. Consultando os endpoints da API (`/api/v1/version` e `/health`), confirmamos a versão exata do software em execução: **Langflow 1.8.2**.

---

## 🚪 2. Acesso Inicial (Initial Access)

Com a versão do software mapeada, o próximo passo lógico foi a busca por vulnerabilidades conhecidas em bases de dados públicas.

* **Vulnerabilidade:** O Langflow 1.8.2 é afetado pela **CVE-2026-33017**, uma falha crítica que permite Execução Remota de Código (RCE) não autenticada via endpoint de build.
* **Vetor de Ataque:** Identificamos que o fluxo público estava vazado e acessível na URL do playground (`7d84d636-af65-42e4-ac38-26e867052c25`).
* **Exploração:** Forjamos uma requisição `POST /api/v1/build_public_tmp/{flow_id}/flow` injetando um script em Python malicioso no payload. A execução desse código no backend nos garantiu uma *reverse shell* com os privilégios do usuário de serviço **www-data**.

---

## 🔄 3. Movimentação Lateral (Lateral Movement)

O acesso inicial limitado exigiu a busca por configurações incorretas e gerenciamento de segredos falho no servidor.

* Inspecionando as variáveis de ambiente do processo que estava rodando sob o `www-data`, localizamos uma credencial de superusuário hardcoded:

```bash
LANGFLOW_SUPERUSER_PASSWORD=n1ghtm4r3_b4_n1ghtf4ll
```

* Aplicando a premissa de reaproveitamento de senhas (*Password Reuse*), testamos essa mesma credencial no serviço SSH.
* O login foi validado com sucesso para o usuário local **nightfall**, garantindo acesso interativo e a leitura da **User Flag**.

---

## 🛡️ 4. Escalação de Privilégios (Privilege Escalation)

### Acesso ao Pod (MCP Server)
A enumeração do diretório home do novo usuário revelou a estrutura da infraestrutura interna.

* Localizamos o arquivo de configuração `.mcp/config.json`, que continha credenciais para um servidor interno MCP (*Model Context Protocol*).
* Analisando a implementação de autenticação desse servidor, descobrimos uma vulnerabilidade criptográfica clássica: a validação JWT aceitava a flag `alg: none`.
* Explorando essa falha, forjamos manualmente um token JWT com privilégios de **admin**.
* Com acesso administrativo na aplicação interna, registramos uma *tool* maliciosa programada para iniciar um callback reverso, entregando uma *shell* diretamente dentro do contêiner do **mcp-server**.

---

## 👑 5. Root (Kubernetes Environment)

O estágio final exigiu abusar das configurações do orquestrador de contêineres para atingir o nó principal.

* A enumeração dentro do pod `mcp-server` revelou que a *Service Account* local possuía permissões excessivas, especificamente a *role* `nodes/proxy`.
* Mapeando a rede interna do cluster, identificamos um pod privilegiado encarregado de monitoramento (`prometheus-node-exporter`), que possuía o sistema de arquivos do *host* principal montado dentro dele.
* Abusando da permissão `nodes/proxy`, nos comunicamos diretamente com a API do kubelet utilizando WebSockets (`/exec`).
* Emitimos um comando para ler o arquivo diretamente da montagem do host:

```bash
cat /host/root/root/root.txt
```

* **Root Flag capturada com sucesso!** 🚩

---
**Cadeia de Exploração (Resumo):**
`Enumeração Web (API Versioning) ➔ Langflow RCE (CVE-2026-33017) ➔ Shell (www-data) ➔ Password Reuse ➔ Shell (nightfall) ➔ JWT alg:none Bypass no MCP ➔ Shell no Pod ➔ Abuso de kubelet exec (nodes/proxy) ➔ Root Host Flag`
